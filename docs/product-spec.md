# 产品需求文档（PRD）

- 产品名：AI 任务管理器
- 产品形态：本地桌面应用，开源、可分发
- 首个目标平台：macOS（本次已完成 arm64 MVP 验收），Linux（规划），Windows（规划）
- 文档状态：产品规划与 MVP 验收基线
- 实现状态：以 [开发验收报告](acceptance.md) 为准
- 更新日期：2026-11-05

> 本文保留完整产品愿景和后续需求。当前实际已验收范围仅为 macOS arm64 MVP；Linux/Windows、Docker 停止、SQLite 历史、菜单栏/tray、自动静默清理和正式性能门禁尚未完成。热压力巡检使用 macOS 公开 API，只读取压力等级，不读取精确温度。

## 1. 产品定义

### 一句话

**把电脑上的进程重新组织成任务，告诉用户谁在消耗资源、哪些可能已经没用了，并帮助用户安全地收掉它们。**

### 产品承诺

在缓存快照可用或首次采集正常完成的条件下，打开应用后 3 秒内，用户应该能回答；10 秒是权限受限或冷启动时的最迟可接受上限：

1. 当前电脑是否处于压力状态？
2. 主要是哪三个任务造成的？
3. 其中有没有明显的浪费或失控？
4. 如果要清理，会关闭什么、会不会误伤？

### 不是什么

- 不是待办事项应用；
- 不是通用进程浏览器的换皮；
- 不是 Docker Desktop 的替代品；
- 不是云端 APM 或 LLM tracing 平台；
- 不是自动“一键优化”的黑盒清理软件；
- 不是未经用户确认就能执行命令的自治 Agent。

## 2. 产品原则

### P1. 任务优先，进程其次

首屏默认展示“任务/工作负载”，进程树作为下钻细节。用户不应该先理解 PID、PPID、PGID、MCP 等系统概念。

### P2. 每个结论必须有证据

“疑似残留”不能只是一个 AI 分数。详情必须展示：

- 任务由哪些进程组成；
- 启动时间和持续时间；
- CPU/内存趋势；
- 是否有子进程持续增长；
- 是否有监听端口；
- 命中了哪条规则；
- 置信度和不确定性。

### P3. 无 AI 也可用

采集、归因、规则检测、清理全部在本地完成。未配置模型时，仍能使用内置问答、筛选和安全清理。

### P4. 默认不联网

遥测默认关闭。远程模型必须由用户主动配置，并在发送前展示将离开本机的数据摘要。

### P5. 安全高于自动化程度

AI 只生成建议。执行动作必须经过确定性策略层、身份校验和用户确认。

### P6. 低打扰、自适应

空闲时不频繁刷新重型指标；异常时才提升采样频率。常驻状态通过菜单栏/托盘摘要呈现。

### P7. 美观、直观与动效是 P0 交付物

视觉质量不是开发完成后的皮肤，而是产品能否被理解、被信任、被传播的核心能力：

- 首屏必须在 3 秒内让用户看出“哪里异常、为什么异常、清理会释放多少”；
- 动效必须解释任务出现、子进程增长、影响范围和动作结果，不做无意义装饰；
- 在 1Hz 数据更新下，布局不抖动、不闪烁、不自动滚动；
- 所有关键信息在 `prefers-reduced-motion`、键盘操作、亮色/暗色主题下仍完整可用；
- README 首图与 20 秒演示 GIF 是发布物的一部分，必须来自真实 UI 和可复现数据。

详细规范见 [视觉、动效与交互设计规范](design-system.md)。

## 3. 核心概念

### Task / 工作负载

用户能理解的一个运行单元。例如：

- `Claude Code · mygo · 修复登录`
- `Codex · 2 个线程 · MCP 进程组`
- `docker compose · mygo-dev`
- `Jupyter · experiments.ipynb`
- `Vite · localhost:5173`
- `PostgreSQL · local`

一个任务包含一个或多个进程，也可能关联一个容器。

### Process / 进程

操作系统层面的真实 PID。展示命令行、父进程、子进程、启动时间、CPU、RSS、端口和状态。

### Evidence / 证据

用于支持归因和风险判断的事实。例如：

- `ppid=82560`
- `same_command_count=12`
- `rss_growth=1.8 GB / 10 min`
- `listening_port=5173`
- `parent_is_ide=true`
- `idle_for=47 min`

### Risk / 风险

分三档，并与颜色和动作分离：

- `healthy`：正常运行；
- `attention`：值得关注，例如持续高 CPU 或较快内存增长；
- `reclaim`：疑似浪费，例如重复 MCP、长时间无活动、子进程爆发。

“reclaim”不是自动删除，只是建议清理。

### Reclaim Candidate / 可回收候选

同时满足资源占用、闲置证据和安全条件的工作负载。需要显示预计回收的 RSS、CPU 和进程数量。

## 4. 用户界面与信息架构

### 导航

- **概览**：系统状态、主要压力来源、浪费摘要、最近异常。
- **任务**：按任务展示运行中的工作负载，支持搜索、筛选和排序。
- **回收站/浪费雷达**：只展示有清理价值且证据充分的候选。
- **AI 助手**：自然语言诊断、筛选与清理计划。
- **设置**：采样、保护名单、模型、外观、隐私和审计日志。

### 视觉签名与开源传播

美观、直观和动效已被提升为 P0 产品目标。对开源桌面工具而言，它们不是“锦上添花”，而是首次理解、下载转化和持续使用的组成部分：用户先通过一张截图判断是否值得安装，再通过一段简短演示判断产品是否可信。视觉设计必须由数据关系驱动，而不是给普通监控器套一层漂亮皮肤。

首发版本确定三个视觉签名：

1. **任务热力树**：树层级表示任务 → 会话 → 进程，面积表示 RSS，同一色相内的明度表示 CPU，图标/边框/纹理表示风险。它让用户直接看到“谁在占内存”，而不是阅读一长串 PID。
2. **生命周期河流**：横轴为时间，每个任务一条泳道，标记进程出生、退出、子进程爆发和长时间低活动。它用来暴露“会话已经结束，但后代进程还在累积”这一核心问题。
3. **爆炸半径预览**：选择回收时，在任务树上直接标出将被停止、受保护、会关闭容器或可能影响 IDE 的节点。危险动作不再依赖一段警告文字。

开源项目的首要演示不是静态首页，而是一段可复现的 20 秒流程：

```text
发现 41 个 MCP 子进程占用 4.8 GB
→ 归因为 6 个会话组
→ 标记其中 12 个长时间无活动的旧组
→ 预览只停止旧组、保留 IDE 和活跃会话
→ 回收 4.2 GB 并写入审计日志
```

仓库应附带合成数据回放模式，让任何人无需配置 Codex/Claude Code 就能运行这段演示。社区可以贡献 Agent 签名和测试夹具，但核心动作策略必须保持审核和确定性。

视觉设计约束：

- 每个可视化必须回答一个明确问题，否则删除；
- 不把红/橙色作为装饰，只用于风险和阻断；
- 数字、单位和时间窗口始终可见；
- 图上任意异常节点都能下钻到证据；
- 不用无解释的“健康分”作为主视觉；
- 风险不能只靠颜色表达，必须有图标、纹理或文本；
- 每个视图最多保留 1–2 个关键动效，空闲时不允许循环动画；
- 动效只表现状态变化，不能承载业务状态或操作结果；
- 1024×720 及以上窗口必须保持主结论、主要动作和证据可见。

### 概览页

首屏结构：

1. **状态带**：CPU、内存、Swap、磁盘 I/O、任务数、Agent 会话数。
2. **一句话结论**：例如“内存压力主要来自 Codex 的 3 个 MCP 进程组，共占用 4.8 GB”。
3. **压力 Top 3 任务卡片**：名称、类型、CPU、内存、持续时间、风险标签。
4. **浪费摘要**：可回收进程数、RSS、检测到的规则。
5. **趋势图**：最近 15 分钟整体资源与任务变化。

禁止使用没有解释的“健康分 62”作为主要信息。若使用评分，必须能展开构成项。

### 任务页

每个任务行展示：

- 图标/类型；
- 任务名；
- 来源（IDE、终端、Docker、系统）；
- 持续时间；
- CPU；
- 内存；
- 子进程数；
- 端口；
- 风险标签；
- 快捷动作。

支持：

- 按 CPU、内存、时长、子进程数排序；
- 按 Agent、开发服务器、容器、实验、系统服务筛选；
- 搜索任务名、命令行、端口、工作目录；
- 固定/忽略任务；
- 展开进程树。

### 任务详情抽屉

分为四个区域：

1. **摘要**：任务身份、总资源、启动时间、置信度。
2. **进程树**：可折叠，突出异常后代和重复命令行。
3. **时间趋势**：CPU/RSS/子进程数量。
4. **证据与建议**：命中规则、风险说明、建议动作、影响范围。

任何停止操作前，从详情抽屉打开确认面板，显示：

- 将收到的信号；
- 预计影响的进程数量和 PID 列表；
- 是否包含受保护进程；
- 是否会停止容器；
- 是否可能影响当前终端/IDE；
- 操作超时与失败处理。

### 浪费雷达

分四类卡片：

- 重复的后台服务/MCP；
- 长时间无活动的 Agent 会话；
- 子进程快速增长的 Agent 根任务；
- 内存持续增长或孤立的工作负载。

每张卡必须包含：

- “为什么认为它可回收”；
- “哪些证据不足”；
- “预计释放多少资源”；
- “安全等级”；
- “查看后清理”按钮。

## 5. 功能优先级

### P0：MVP 必须有

#### 5.1 实时系统概览

- CPU 使用率；
- 物理内存与 Swap 压力；
- 磁盘读写速率；
- 网络速率；
- 进程数、任务数；
- 系统热压力等级（macOS 公开 `thermalState`：Nominal / Fair / Serious / Critical）；
- 1 秒–2 秒采样，异常时自适应提速。

验收标准：

- 数据来源真实，不可用时显示“不可用”而不是 0；
- 不展示虚构摄氏度；热压力不可用时明确说明公开 API 限制；
- Serious 连续 60 秒、Critical 立即触发一次低打扰提示，并把压力归因到有证据的任务；
- 刷新不阻塞 UI；
- 退出应用后不残留采集进程。

#### 5.2 任务归因

至少支持以下识别：

- Claude Code、Codex、Gemini CLI、OpenCode、Aider、Goose；
- IDE：VS Code、Cursor、Windsurf、JetBrains 系列；
- 终端和 Shell；
- Node/Python/Bun/Go/Java 开发服务器；
- Jupyter kernel；
- Docker 容器与 Compose 项目；
- 常见 MCP server（Node、Python、uv、Docker）；
- 系统和系统代理进程。

归因输入：

- PID、PPID、PGID、Session；
- 可执行文件、命令行；
- 工作目录（权限允许时）；
- 父进程链；
- 起止时间；
- 监听端口；
- Docker 标签和容器元数据；
- 可选环境标签。

验收标准：

- 对测试夹具中的 20 组典型任务，根任务归因正确率 ≥ 90%；
- 每个任务显示置信度；
- 用户手动合并/拆分后，下次同类任务可复用规则；
- 无法归因的进程进入“未归类进程”，不强行猜测。

#### 5.3 异常与浪费检测

MVP 规则：

1. **重复 MCP/后台服务**：同一 Agent 根下有多个相同或近似的长期子进程；
2. **Agent 子进程爆发**：后代数量在短时间内快速增加，或超过配置阈值；
3. **疑似闲置会话**：Agent 根任务长时间低 CPU、无端口变化，且启动时间较早；
4. **内存持续增长**：RSS 在滑动窗口内持续上升并超过阈值；
5. **浏览器/工具 helper 堆积**：同一父进程下大量相似 `node_repl`、`playwright`、浏览器 helper；
6. **孤立任务**：父进程已消失、任务仍在运行且符合用户启动任务特征；
7. **端口占用**：展示监听端口与任务映射，辅助解决端口冲突。

验收标准：

- 每条告警包含触发指标、阈值、持续时间和证据；
- 阈值可在设置中调整；
- 同一任务 10 分钟内不重复弹出相同通知；
- 规则不使用“AI 猜测”作为唯一依据。

#### 5.4 安全回收

- 优雅停止任务树；
- 优先向子进程发送终止请求，再处理根进程；
- 等待超时后允许用户选择强制结束；
- 容器使用引擎 API 停止，不执行未经验证的 shell 字符串；
- 系统关键进程不可操作；
- 当前应用自身、祖先 Shell、IDE 默认受保护；
- PID 复用检查：动作前再次验证 PID 与启动时间。

验收标准：

- 默认不会发送 SIGKILL；
- 不经过确认不能执行任何终止动作；
- 受保护进程不可被 Agent 或批量规则绕过；
- 操作结果和失败原因写入本地审计日志；
- 自动化测试证明不会误杀测试中的父 Shell。

#### 5.5 AI 助手

支持四类意图：

1. **诊断**：“为什么我的电脑这么卡？”
2. **检索**：“找出所有跑了超过 2 小时的 Claude 会话。”
3. **解释**：“这个任务是什么？为什么被标成可回收？”
4. **计划**：“给我一个安全的清理方案，不要动 VSCode。”

交互要求：

- 回答引用当前快照中的任务、PID、指标和时间窗口；
- 明确区分事实、推断和建议；
- 生成清理计划时按影响范围排序；
- 用户点击“执行”后仍走统一确认流程；
- 模型不可用或不稳定时，降级为内置筛选和规则问答；
- 支持 OpenAI-compatible 端点（OpenAI、Ollama、LM Studio、vLLM 等）；
- API key 存储在系统钥匙串或本地安全存储，不写入日志。

验收标准：

- 未配置模型时可完成至少 8 个内置诊断问题；
- 模型回答不能直接触发停止操作；
- 发送远程请求前显示将发送的数据类别，并默认脱敏命令行中的 token、key、password、cookie 等字段；
- 用户可完全关闭 AI 网络请求。

#### 5.6 本地历史与通知

- 保留最近 7 天的任务/资源聚合数据；
- 默认只保存聚合指标，不保存完整命令行；
- 异常持续达到阈值后发送系统通知；
- 用户可从通知直接打开任务详情。

当前 0.2.0 已实现其中的热压力通知闭环：后台每 25 秒巡检、Serious 连续 60 秒提示、Critical 立即提示、同原因 15 分钟冷却、点击通知恢复窗口。通知内容经过脱敏，且不会触发清理动作。持久历史仍属于后续范围。

#### 5.7 设置与保护名单

- 采样频率；
- 告警阈值；
- 受保护任务/进程；
- 忽略列表；
- 模型配置；
- 远程数据开关；
- 清理历史与导出。

#### 5.8 视觉质量、动效与首屏体验

本项与采集、归因、安全回收同为 P0，不允许推迟到“最后美化”。

必须交付：

- 完整暗色与亮色主题，默认跟随系统；
- Signal Deck 设计语言与统一 design tokens；
- 任务热力树、生命周期河流、爆炸半径预览三个签名视图；
- 任务行到详情抽屉的空间连续转场；
- 风险、受保护、阻断、动作中、动作结果五种状态的统一视觉语义；
- 可复现的合成数据回放模式，用于 README GIF 和社区演示；
- 可访问性降级：图表文本摘要、键盘操作、reduced-motion；
- 本地打包字体与图标，不依赖远程资源。

验收标准：

- 首屏 1 秒内形成明确视觉层级：结论、Top 压力任务、可回收容量中至少两项可见；
- 打开应用 3 秒内可说出当前主要压力来源；
- 1Hz 采样更新时主线程单次处理 <16ms，CLS <0.05，无明显布局跳动；
- 动画运行稳定 60fps，采样更新期间无 >50ms 长任务；
- 空闲状态没有持续循环动画；
- `prefers-reduced-motion` 下所有信息和操作完整；
- 1440×900 和 1024×720 均无关键内容截断；
- 暗色/亮色正文对比度均 ≥4.5:1；
- README 首图和演示 GIF 在公开 beta 前完成，且必须来自真实 UI；
- 用户能从爆炸半径预览中正确识别“将停止”和“受保护”两类节点。

### P1：首个公开版本后

- 菜单栏 flyout：当前压力、Top 1 任务、快速打开主窗口；
- 历史对比：今天 vs 过去 7 天；
- 任务命名规则编辑器和导入/导出；
- Agent 启动包装器：`aitm run -- claude`，为零配置归因提供高置信标签；
- Docker Compose 项目级资源汇总；
- GPU 支持：按平台逐步实现 NVIDIA/AMD/Apple；
- 导出诊断报告 Markdown；
- 只读 MCP server，让其他 Agent 能查询系统状态；
- 通知中的“稍后提醒”和规则抑制。

### P2：后续

- 远程/多机监控；
- 智能体工作流 trace 导入（OpenTelemetry）；
- 团队共享诊断快照；
- 插件系统；
- 自动化规则（仍受确认策略约束）；
- 多用户/服务器模式。

## 6. AI 设计约束

### 6.1 事实层与模型层分离

```text
采集器 → 结构化快照 → 归因引擎 → 规则引擎 → AI 解释/规划 → 用户确认 → 动作执行
```

LLM 不直接读取 `/proc`，不直接执行 shell，也不决定“是否可以杀”。它接收经过脱敏的结构化上下文。

### 6.2 上下文包

只发送必要字段：

- 任务名、类型、持续时间；
- CPU/RSS 趋势摘要；
- 子进程数量与重复度；
- 端口；
- 检测规则与证据；
- 用户问题；
- 用户明确允许的任务详情。

默认不发送：

- 完整环境变量；
- 命令行中的密钥；
- 文件内容；
- 对话记录；
- 与问题无关的进程列表。

### 6.3 回答规范

每个结论尽量采用：

- **事实**：来自采集数据；
- **推断**：来自规则/AI；
- **建议**：下一步动作；
- **不确定**：缺少哪项证据。

示例：

> 事实：Codex app-server 下有 41 个 `node` 子进程，合计 4.2 GB RSS，过去 8 分钟增加了 17 个。  
> 推断：高度疑似 MCP 进程未随线程结束而回收。  
> 建议：先停掉最旧的 12 个重复 MCP 子进程组，而不是结束整个 Codex。  
> 不确定：当前无法确认这些线程是否仍在使用中，请先查看进程树。

## 7. 安全与隐私要求

### 必须保护

- 应用自身、父进程和祖先链；
- 当前用户登录 Shell、SSH 会话；
- WindowServer、launchd、systemd、kernel_task 等系统关键进程；
- 用户显式保护的任务；
- 当前前台 IDE/终端（默认保护，可显式解除）；
- Docker daemon 和容器运行时。

### 操作策略

- 默认只操作系统当前用户拥有的进程；
- 不做全局 `pkill -f` 式模糊匹配；
- 每个动作绑定 PID + 启动时间 + 任务 ID；
- 优雅终止 → 超时 → 再确认强杀；
- 动作过程中实时展示每个 PID 的结果；
- 失败可重试，不隐藏错误。

### 隐私

- 无默认遥测；
- 本地数据库位于应用数据目录；
- 不保存 API key 明文；
- 提供“清空历史”；
- 远程模型开关默认关闭；
- 在日志中脱敏常见敏感参数。

## 8. 指标与成功标准

### 用户价值指标

- 首次诊断时间：从打开应用到看到主要压力来源目标 < 3 秒，冷启动硬上限 < 10 秒；
- 清理耗时：从发现候选到完成安全清理 < 30 秒；
- 任务归因正确率：测试集 ≥ 90%；
- 用户现场纠正率：首版 < 15%；
- 误杀率：0（必须通过保护策略和确认流程保证）；
- 用户在一次清理后 5 分钟内重复手动清理的比例下降。

### 视觉与体验指标

- 首屏视觉层级形成：<1 秒；
- 3 秒内说出主要压力任务：可用性测试中 ≥80%；
- 20 秒演示 GIF 能独立讲清“发现 → 归因 → 预览 → 回收”：≥80% 的测试者能复述；
- 爆炸半径预览中的“将停止 / 受保护”识别正确率：≥90%；
- 正常采样更新 P95 帧时间：<16.7ms；
- CLS：<0.05；
- 空闲持续动画：0；
- 关键界面在 reduced-motion 下功能完整率：100%。

### 性能预算

- 应用常驻 CPU 平均 < 1.5%（8 核参考机）；
- UI 内存目标稳定 <250MB RSS；
- 空闲时 UI 无持续动画；
- 采样不导致风扇持续启动；
- 本地数据库 7 天 < 200 MB；
- 采集失败时 UI 仍可用。

### 质量指标

- 关键平台采集器有 golden tests；
- 动作执行器有真实子进程集成测试；
- UI 覆盖空状态、权限不足、容器不可用、模型失败；
- UI 覆盖暗色/亮色、键盘焦点、200% 缩放和 reduced-motion；
- 1440×900 与 1024×720 的视觉回归截图通过；
- 崩溃后不留下后台子进程。

## 9. 发布边界

### MVP 支持

- macOS：完整任务归因、Agent 检测、Docker、端口、安全清理；
- Linux：进程树、端口、Docker、基础清理；
- Windows：基础进程与资源展示，任务归因与清理标记为 experimental。

### 推荐首发楔子

完整产品长期覆盖 Agent、实验、开发服务器和容器，但首个公开版本应收窄为一个足够尖锐的场景：

> **macOS 上 Codex / Claude Code 的 MCP 与 sub-agent 资源堆积诊断和安全回收。**

首发版本只允许回收“有明确宿主关系的重复或孤立后代进程组”以及用户选中的容器；不提供对任意系统进程或整个 IDE 的通用终止能力。先用一个高频、强痛点证明归因和安全模型，再扩展到更多工作负载。

### MVP 不支持

- GPU/能耗的完整支持；
- 精确摄氏度读数（macOS 公开 API 不提供，且不使用 SMC、root 或 `powermetrics`）；
- 远程机器；
- 自动清理；
- 直接接管 Agent 对话；
- 对所有第三方 MCP 的精确语义理解；
- 无权限读取系统进程完整详情；
- 跨用户会话操作。

## 10. 产品成立条件

MVP 不是以“功能数量”判定完成，而是以以下五件事同时成立判定：

1. **3 秒定位**：首屏能指出主要压力任务，而不是让用户自己关联 PID；冷启动最迟不超过 10 秒。
2. **证据可理解**：用户能复述为什么一个任务被标记为异常或疑似可回收。
3. **动作可信任**：停止前能准确预览影响范围；测试环境中零误杀。
4. **无 AI 可闭环**：没有配置模型时，发现、筛选和清理仍完整可用。
5. **一眼值得用**：视觉层级清楚、60fps 稳定、危险范围可见，并能在真实截图中讲清“为什么值得安装”。

若只能完成一个功能，应优先完成“重复 MCP / Agent 子进程堆积”的识别与安全清理，因为它同时覆盖归因、证据、动作三个核心价值。通用资源曲线和聊天框都不能单独证明产品成立。

## 11. 后续验证计划

在开始大规模功能开发前，用可交互原型验证四个假设：

1. 用户是否能理解“任务/工作负载”这个抽象，并愿意用它替代进程列表；
2. “证据 + 预览 + 确认”是否足以降低清理焦虑；
3. AI 问答是否比手动筛选明显缩短定位时间；
4. 用户能否仅凭首屏截图或 20 秒 GIF 理解主要问题和回收边界。

建议测试 8–12 名高频使用 AI Agent 的开发者，记录：

- 从发现问题到定位任务的时间；
- 从定位到决定清理的时间；
- 对风险标签的信任程度；
- 对误杀的担忧；
- 对热力树、生命周期河流和爆炸半径预览的理解程度；
- 从截图/GIF 中复述产品价值的能力；
- 最常用的筛选和提问；
- 是否愿意长期保留常驻应用。
